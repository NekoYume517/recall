# recall 算法与实现说明

记录几个不显然的技术判断，以及交叉审查中发现的真实 bug。每一条都有对应的回归测试。

## 1. SM-2 的 q 映射不等于 Grade 的整数刻度

这是最容易搞错的一处，项目里出现过两次。

`Grade` 是 4 档枚举，`to_int` 给出的是**展示用**的 0..5 刻度：

```
Again=0, Hard=2, Good=3, Easy=5
```

但 SM-2 公式里的 `q` 是 0..5 的**评分**，映射是另一套：

```
Again=2, Hard=3, Good=4, Easy=5
```

**两者不能混用**。`to_int` 是为了打印好看（契合 Anki 的 0-5 界面），`q` 是为了代入公式。

用错的后果（实测）：

```
Good, Good, Again, Good
  正确（q=2）：EF = 2.5 → 2.5 → 2.18 → 2.18
  错误（q=0）：EF = 2.5 → 2.5 → 1.70 → 1.70
```

`q=2` 的增量是 `0.1 - 3*(0.08+3*0.02) = -0.32`；`q=0` 的增量是 `0.1 - 5*(0.08+5*0.02) = -0.80`。差一倍多。

**同时注意**：「答错」的判定是 `q < 3`，而 `Hard` 的 `q = 3`，所以 **Hard 算答对**。这与 `Grade::is_pass` 如果写成 `to_int() >= 3` 会把 Hard 判成失败——项目里出现过这个 bug，已用 `is_recalled(g) = g != Again` 统一。

## 2. EF 用更新前的值算间隔

SM-2 原文的顺序是：

```
1. 用当前的 EF 算新间隔
2. 再更新 EF
```

反过来会让每次间隔都偏大。`Good × 5` 的正确序列是 `1, 6, 15, 38, 95`（EF 恒为 2.5，因为 `q=4` 时增量为 0）。

权威参考表（手算 + 独立实现双重核对）：

| 序列 | interval | EF |
|---|---|---|
| Good ×5 | 1, 6, 15, 38, 95 | 2.5 恒定 |
| Easy ×3 | 1, 6, 16 | 2.6, 2.7, 2.8 |
| Hard ×3 | 1, 6, 13 | 2.36, 2.22, 2.08 |
| Good, Good, Again, Good | 1, 6, 1, 1 | 2.5, 2.5, 2.18, 2.18 |

## 3. FSRS 的定义性不变量

`S` 的定义就是「回忆概率衰减到 90% 所需的天数」。这直接给出了可测试的恒等式：

```
R(t = S, S) = (1 + 19/81 * 1)^(-0.5) = (100/81)^(-0.5) = 0.9
```

以及：

```
interval_days(S, 0.9) = S / FACTOR * (0.9^(1/-0.5) - 1)
                      = S / (19/81) * (0.9^-2 - 1)
                      = S / (19/81) * (19/81)
                      = S                    ← 未取整前精确相等
```

这两条比逐个数值比对更能抓住实现错误——任何公式符号写反、常数写错都会破坏它们。

## 4. 难度更新缺 linear damping（真实 bug）

FSRS-5 的难度增量是：

```
delta_D = -w[6] * (g - 3) * (10 - D) / 9
```

最初的实现漏了最后的 `(10-D)/9`。后果：

| 当前 D | 无阻尼增量 | 有阻尼增量 |
|---|---|---|
| 1.0 | +2.9208 | +2.9208 |
| 5.0 | +2.9208 | +1.6227 |
| 9.9 | +2.9208 | +0.0325 |

无阻尼时**增量与当前难度完全无关**。一张已经 D=9 的卡再来一次 Again，直接顶到 10 并永远卡住。带阻尼时是饱和收敛：`8.62 → 9.04 → 9.33 → 9.52 → 9.64`。

**后果**：难度失去分辨率。D 顶到 10 后 `(11-D) = 1`，稳定性增益接近最大，会**系统性高估难卡的间隔增长**——正好与 FSRS 的设计意图相反。

实测影响：修正后 90 天模拟的复习量从 9014 降到 7735（−14%），因为旧版把间隔虚假拉长了。

## 5. mean reversion 的目标是 D_0(4)，不是 w[4]

```
正确:  D'' = w[7] * D_0(4) + (1 - w[7]) * D'
错误:  D'' = w[7] * w[4]   + (1 - w[7]) * D'
```

- `w[4] = 7.1949` 是 D_0 公式里的常数项
- `D_0(4) = w[4] - exp(w[5]*3) + 1 = 3.2245` 是实际的初始难度

官方 py-fsrs 参考实现用 `D_0(4)`。两者差 3.97，虽然 `w[7] = 0.0046` 让单步影响只有 0.018，但方向性错误会累积。

## 6. 稳定性更新使用复习前的 D

官方顺序：

```
1. 计算 R（用旧 S）
2. 从旧 D 计算新 D
3. 用旧 D 计算 S'
```

参考 [fsrs4anki v5.3.0](https://github.com/open-spaced-repetition/fsrs4anki/blob/v5.3.0/fsrs4anki_scheduler.js)
的 review 分支，成功和遗忘的稳定性更新都接收 `last_d`。本库保留公式原值，
不使用参考 UI 的两位小数显示舍入与 fuzz。Good × 5 的取整间隔为
3 → 11 → 35 → 101 → 269 天。

注意 R 仍然用**旧 S**——R 描述的是"这一刻的可提取性"，不该被新状态污染。

## 7. Int64 回绕（真实 bug）

FSRS 连续 Easy 到第 46 次时，`interval = 4.19e14` 天。`due = now + interval * 86400` 超过 Int64 上限，**回绕成负数**：

```
due = -7085176555797265162
```

后果：`due` 为负 → `is_due()` 永远为 true → 卡片永久到期 → replay / simulate / stats 全部崩坏。

**修复**：`add_days` 和 `interval_days` 双层夹取到 `max_interval_days() = 36500`（100 年），并处理 NaN 与负数。

这个 bug 只有在数据规模足够大时才暴露——原来 5 次复习只跑到 `1, 6, 15, 38, 95`，根本到不了爆炸区间。**扩展样例数据直接换来了 bug 发现**。

## 8. SM-2 的间隔也会指数爆炸（真实 bug）

`interval = round(interval_prev * EF)`，一直答对时是纯几何增长。30 次复习后：

```
g2: 3,210,805,085,223 天（约 88 亿年）
```

同样要夹到 36500。

**这也暴露了一个指标解读陷阱**：当前示例中 SM-2 的总间隔约为 FSRS 的 13 倍，看起来 SM-2 "更好"。实际上 25 张卡里有 4 张顶到 100 年上限——算法认为它们"100 年后才需要复习"，这在现实中等同于**永远不再复习**，等价于遗忘。

所以 `compare` 现在单独列出「触及上限卡数」，并明确说明间隔总和在此不可直接比较。

## 9. 模拟器的评分策略拿不到真实时间（真实 bug）

`grade_fn` 签名是 `(CardState) -> Grade`，**没有 `now`**。所以策略只能用 `interval_days`（计划间隔）当"已过天数"：

```
elapsed = cs.interval_days       // 这是「计划间隔」，不是真实流逝时间
```

一张卡被积压拖到逾期 30 天，真实 R 早已远低于 0.9，但策略仍算它"刚到点、记得很牢"。

**实测症状**：

```
day 0-19   记住率 = 0.883
day 40-59  记住率 = 0.898    ← 积压 752 张，记住率反而「升高」
```

积压不恶化记忆 → 积压数被系统性低估 → 「越拖越忘 → 更多 Again → 间隔回退」这条自我强化回路完全失效。

**修复**（不改 `grade_fn` 签名）：`simulate_with` 手里有 `now`，把传给评分器的**状态副本**里的 `interval_days` 换成真实 elapsed，`review` 仍收原始状态：

```moonbit
let elapsed_real = days_between(before.last_review, now)
let for_grading = { ..before, interval_days: elapsed_real }
let g = (config.grade_fn)(for_grading)
states[idx] = s.review(before, g, now)
```

修复后：`--review-limit 50` 的 90 天积压从 760 变成 **1337**（原来的数字是乐观下界）。

## 10. 确定性要求

模拟器必须可复现，否则无法测试、也无法对比。所有随机用固定 seed 的 LCG：

```moonbit
self.state = (self.state * 1103515245 + 12345) & 0x7FFFFFFF
```

注意 `Int` 是 32 位，乘法必须用 Int64 或及时掩码，否则溢出成负数。

## 11. 样例数据的设计

`examples/reviews.jsonl` 由 `scripts/gen_reviews.py` 生成，遵守两条硬约束：

**(a) `elapsed_days` 必须严格等于相邻事件 `reviewed_at` 的时间戳差 / 86400**

否则 `replay`（用时间戳算间隔）与 `retention_curve`（用字段分桶）会给出互相矛盾的结论。生成时用时间戳反算字段值，从源头杜绝不一致（自检输出 0 mismatches）。

**(b) 评分由遗忘曲线决定，而不是手填**

```python
R = (1 + 19/81 * t/S) ** -0.5
记不记得 = rng.uniform() < R
```

这样 lapses **天然**集中在长间隔，保留率曲线的单调性成为数据的必然结果，而不是拟合假象。

当前规模：25 张卡 × 30 次复习 = 750 事件，遗忘率 17.6%，保留率曲线 91.8% → 50.0%。

**注意曲线仍有桶间抖动**（如 91.8 → 80.2 → 54.9 → 74.3）。这是小样本统计的固有特性，不是 bug：后 7 个桶每桶 9-39 个样本，二项分布标准差约 11%，所以 55% ↔ 75% 的波动在期望范围内。CLI 的「曲线出现回升（样本噪声，或分桶过细）」告警是准确的诊断。

## 12. 验证方法

- **SM-2**：四组手算表逐项比对，含 `Good,Good,Again,Good` 的 EF=2.18
- **FSRS**：`R(t=S)=0.9` 与 `interval_days(S,0.9)=S` 两个恒等式，多组 S 验证（0.4 / 3.17 / 15.69 / 365）
- **交叉审查**：固定 FSRS-5 官方参考版本，核对 linear damping、mean reversion 目标和旧 D 状态转移。
- **回归保护**：稳定性测试同时验证官方 `last_d` 路径和独立数值锚点，防止把新 D 反馈进同一次稳定性计算。
