# recall 算法与实现说明

记录几个不显然的技术判断，以及交叉审查中发现的真实 bug。每一条都有对应的回归测试。

## 1. SM-2 的 q 映射不等于 Grade 的整数刻度

这是最容易搞错的一处，项目里出现过两次。

`Grade` 是 4 档枚举，`to_int` 给出的是**展示用**的 0..5 刻度：

```
Again=0, Hard=2, Good=3, Easy=5
```

但 SM-2 公式里的 `q` 是 0..5 的**评分**，映射是另一套：

```
Again=2, Hard=3, Good=4, Easy=5
```

**两者不能混用**。`to_int` 是为了打印好看（契合 Anki 的 0-5 界面），`q` 是为了代入公式。

用错的后果（实测）：

```
Good, Good, Again, Good
  正确（q=2）：EF = 2.5 → 2.5 → 2.18 → 2.18
  错误（q=0）：EF = 2.5 → 2.5 → 1.70 → 1.70
```

`q=2` 的增量是 `0.1 - 3*(0.08+3*0.02) = -0.32`；`q=0` 的增量是 `0.1 - 5*(0.08+5*0.02) = -0.80`。差一倍多。

**同时注意**：「答错」的判定是 `q < 3`，而 `Hard` 的 `q = 3`，所以 **Hard 算答对**。这与 `Grade::is_pass` 如果写成 `to_int() >= 3` 会把 Hard 判成失败——项目里出现过这个 bug，已用 `is_recalled(g) = g != Again` 统一。

## 2. EF 用更新前的值算间隔

SM-2 原文的顺序是：

```
1. 用当前的 EF 算新间隔
2. 再更新 EF
```

反过来会让每次间隔都偏大。`Good × 5` 的正确序列是 `1, 6, 15, 38, 95`（EF 恒为 2.5，因为 `q=4` 时增量为 0）。

权威参考表（手算 + 独立实现双重核对）：

| 序列 | interval | EF |
|---|---|---|
| Good ×5 | 1, 6, 15, 38, 95 | 2.5 恒定 |
| Easy ×3 | 1, 6, 16 | 2.6, 2.7, 2.8 |
| Hard ×3 | 1, 6, 13 | 2.36, 2.22, 2.08 |
| Good, Good, Again, Good | 1, 6, 1, 1 | 2.5, 2.5, 2.18, 2.18 |

## 3. FSRS 的定义性不变量

`S` 的定义就是「回忆概率衰减到 90% 所需的天数」。这直接给出了可测试的恒等式：

```
R(t = S, S) = (1 + 19/81 * 1)^(-0.5) = (100/81)^(-0.5) = 0.9
```

以及：

```
interval_days(S, 0.9) = S / FACTOR * (0.9^(1/-0.5) - 1)
                      = S / (19/81) * (0.9^-2 - 1)
                      = S / (19/81) * (19/81)
                      = S                    ← 未取整前精确相等
```

这两条比逐个数值比对更能抓住实现错误——任何公式符号写反、常数写错都会破坏它们。

## 4. 难度更新缺 linear damping（真实 bug）

FSRS-5 的难度增量是：

```
delta_D = -w[6] * (g - 3) * (10 - D) / 9
```

最初的实现漏了最后的 `(10-D)/9`。后果：

| 当前 D | 无阻尼增量 | 有阻尼增量 |
|---|---|---|
| 1.0 | +2.9208 | +2.9208 |
| 5.0 | +2.9208 | +1.6227 |
| 9.9 | +2.9208 | +0.0325 |

无阻尼时**增量与当前难度完全无关**。一张已经 D=9 的卡再来一次 Again，直接顶到 10 并永远卡住。带阻尼时是饱和收敛：`8.62 → 9.04 → 9.33 → 9.52 → 9.64`。

**后果**：难度失去分辨率。D 顶到 10 后 `(11-D) = 1`，稳定性增益接近最大，会**系统性高估难卡的间隔增长**——正好与 FSRS 的设计意图相反。

该项修复的历史对照为 9014 → 7735 次复习。完成旧 D 状态转移修正后，
当前固定种子、90 天、每天 20 张新卡、复习上限 200 的结果为 7706 次。

## 5. mean reversion 的目标是 D_0(4)，不是 w[4]

```
正确:  D'' = w[7] * D_0(4) + (1 - w[7]) * D'
错误:  D'' = w[7] * w[4]   + (1 - w[7]) * D'
```

- `w[4] = 7.1949` 是 D_0 公式里的常数项
- `D_0(4) = w[4] - exp(w[5]*3) + 1 = 3.2245` 是实际的初始难度

官方 py-fsrs 参考实现用 `D_0(4)`。两者差 3.97，虽然 `w[7] = 0.0046` 让单步影响只有 0.018，但方向性错误会累积。

## 6. 稳定性更新使用复习前的 D

官方顺序：

```
1. 计算 R（用旧 S）
2. 从旧 D 计算新 D
3. 用旧 D 计算 S'
```

参考 [fsrs4anki v5.3.0](https://github.com/open-spaced-repetition/fsrs4anki/blob/v5.3.0/fsrs4anki_scheduler.js)
的 review 分支，成功和遗忘的稳定性更新都接收 `last_d`。本库保留公式原值，
不使用参考 UI 的两位小数显示舍入与 fuzz。Good × 5 的取整间隔为
3 → 11 → 35 → 101 → 269 天。

注意 R 仍然用**旧 S**——R 描述的是"这一刻的可提取性"，不该被新状态污染。

### 6.1 遗忘上限是短期的（真实 bug）

同一节里还有一条容易被抄错的常数：`S_f` 的上限。FSRS-4.5 写
`min(raw, S)`，FSRS-5 改成 `min(raw, S / exp(w17·w18))`，并且**只在
`enable_short_term` 打开时**用后者。本库的 `step` 对 `elapsed < 1` 就是按
w17/w18 做短期更新的，所以两条分支必须同一个假设。

修复前用的是 4.5 的 `min(raw, S)`，默认权重下 `exp(w17·w18) = 1.40777`，
于是遗忘后的稳定性可以比官方高 40.8%（D=3、S=22.75、R=0.05：22.75 vs
16.16），间隔随之偏长——「记不住却排得更远」的一类静默错误。
对照点是 py-fsrs 5.1.3 `Scheduler._next_forget_stability`：
`min(2.5648860200305696, 3/1.4077712147375412) = 2.1310280879406296`。

### 6.2 间隔取整用 half-up，不是银行家舍入

`interval_days` 用 `@math.round`（half-up：`round(2.5)=3`），py-fsrs 用
Python 的 `round`（half-to-even：`round(2.5)=2`）。间隔恰好落在 `k+0.5`
时本实现可能多 1 天。这是刻意保留的差异：half-up 与 SM-2 一侧用同一个
`@math.round`，同一份代码里不会出现两套舍入。**不要为此改实现**，
除非同时改掉 SM-2 的取整并重算 `sm2_test.mbt` 的四组手算表。

## 7. Int64 回绕（真实 bug）

FSRS 连续 Easy 到第 46 次时，`interval = 4.19e14` 天。`due = now + interval * 86400` 超过 Int64 上限，**回绕成负数**：

```
due = -7085176555797265162
```

后果：`due` 为负 → `is_due()` 永远为 true → 卡片永久到期 → replay / simulate / stats 全部崩坏。

**修复**：`add_days` 和 `interval_days` 双层夹取到 `max_interval_days() = 36500`（100 年），并处理 NaN 与负数。

这个 bug 只有在数据规模足够大时才暴露——原来 5 次复习只跑到 `1, 6, 15, 38, 95`，根本到不了爆炸区间。**扩展样例数据直接换来了 bug 发现**。

## 8. SM-2 的间隔也会指数爆炸（真实 bug）

`interval = round(interval_prev * EF)`，一直答对时是纯几何增长。30 次复习后：

```
g2: 3,210,805,085,223 天（约 88 亿年）
```

同样要夹到 36500。

**这也暴露了一个指标解读陷阱**：当前示例中 SM-2 的总间隔约为 FSRS 的 13 倍，看起来 SM-2 "更好"。实际上 25 张卡里有 4 张顶到 100 年上限——算法认为它们"100 年后才需要复习"，这在现实中等同于**永远不再复习**，等价于遗忘。

所以 `compare` 现在单独列出「触及上限卡数」，并明确说明间隔总和在此不可直接比较。

## 9. 模拟器的评分策略拿不到真实时间（真实 bug）

`grade_fn` 签名是 `(CardState) -> Grade`，**没有 `now`**。所以策略只能用 `interval_days`（计划间隔）当"已过天数"：

```
elapsed = cs.interval_days       // 这是「计划间隔」，不是真实流逝时间
```

一张卡被积压拖到逾期 30 天，真实 R 早已远低于 0.9，但策略仍算它"刚到点、记得很牢"。

**实测症状**：

```
day 0-19   记住率 = 0.883
day 40-59  记住率 = 0.898    ← 积压 752 张，记住率反而「升高」
```

积压不恶化记忆 → 积压数被系统性低估 → 「越拖越忘 → 更多 Again → 间隔回退」这条自我强化回路完全失效。

**修复**（不改 `grade_fn` 签名）：`simulate_with` 手里有 `now`，把传给评分器的**状态副本**里的 `interval_days` 换成真实 elapsed，`review` 仍收原始状态：

```moonbit
let elapsed_real = days_between(before.last_review, now)
let for_grading = { ..before, interval_days: elapsed_real }
let g = (config.grade_fn)(for_grading)
states[idx] = s.review(before, g, now)
```

该项修复的历史对照为 760 → 1337 张。完成 FSRS 状态转移修正后，
当前 `--review-limit 50` 的 90 天最终积压为 **1294** 张。

## 10. 确定性要求

模拟器必须可复现，否则无法测试、也无法对比。所有随机用固定 seed 的 LCG：

```moonbit
self.state = (self.state * 1103515245 + 12345) & 0x7FFFFFFF
```

注意 `Int` 是 32 位，乘法必须用 Int64 或及时掩码，否则溢出成负数。

## 11. 样例数据的设计

`examples/reviews.jsonl` 由 `scripts/gen_reviews.py` 生成，遵守两条硬约束：

**(a) `elapsed_days` 必须严格等于相邻事件 `reviewed_at` 的时间戳差 / 86400**

否则 `replay`（用时间戳算间隔）与 `retention_curve`（用字段分桶）会给出互相矛盾的结论。生成时用时间戳反算字段值，从源头杜绝不一致（自检输出 0 mismatches）。

**(b) 评分由遗忘曲线决定，而不是手填**

```python
R = (1 + 19/81 * t/S) ** -0.5
记不记得 = rng.uniform() < R
```

这样 lapses **天然**集中在长间隔，保留率曲线的单调性成为数据的必然结果，而不是拟合假象。

当前规模：25 张卡 × 30 次复习 = 750 事件，遗忘率 17.6%，保留率曲线 91.8% → 50.0%。

**注意曲线仍有桶间抖动**（如 91.8 → 80.2 → 54.9 → 74.3）。这是小样本统计的固有特性，不是 bug：后 7 个桶每桶 9-39 个样本，二项分布标准差约 11%，所以 55% ↔ 75% 的波动在期望范围内。CLI 的「曲线出现回升（样本噪声，或分桶过细）」告警是准确的诊断。

**桶标签是四舍五入后的显示值**（不是精确桶沿）：精度跟着桶宽走（桶宽 ≥ 1 天用 1 位小数、0.1–1 天用 2 位，再窄依次加位）。桶沿是 `max/n·k` 这样的有理数，一般不能有限位十进制精确表示，所以极端边界上标签会与真实桶沿差最后一位（`--buckets 10`、最大间隔 100.6 时样本 10.08 落在桶 1，标签是 `[10.1, 20.1)`）。归桶与统计始终用未取整的上下界，精确判定以 `retention_curve` 返回值为准——口径见 `docs/DEMO.md` §6。

## 12. 验证方法

- **SM-2**：四组手算表逐项比对，含 `Good,Good,Again,Good` 的 EF=2.18
- **FSRS**：`R(t=S)=0.9` 与 `interval_days(S,0.9)=S` 两个恒等式。后者只在
  `S ∈ [1, 36500]` 内成立（S<1 夹到 1 天、S>36500 截到 100 年上限），
  多组 S 验证（0.4 / 3.17 / 15.69 / 365）并单独锁定夹取边界
- **交叉审查**：固定 FSRS-5 官方参考版本，核对 linear damping、mean reversion 目标和旧 D 状态转移。
- **回归保护**：稳定性测试同时验证官方 `last_d` 路径和独立数值锚点，防止把新 D 反馈进同一次稳定性计算。

## 13. 迁移提示：`interval_error_days` 的口径（2026-11-27，第十九轮）

**从第十九轮起，`replay` 的 `interval_error_days` 用日志 `due_at` 当计划值**
（`计划间隔 = (due_at − 上一条 reviewed_at) / 86400`，负数按 0；首条事件无前驱，
沿用调度器初始值）。此前实现取的是「重放到此刻的调度器自己算出的间隔」，与
`due_at` 无关——修前修后是**两套语义**，读数会变：`examples/reviews.jsonl` 上
由 `421.02 天` 变为 `4.02 天`（旧口径是「用户节奏 vs 调度器理想间隔」，新口径是
「计划 vs 实际」）。下游若按旧数值写过判据，需要改判据而不是改实现——API.md
第 4 节的契约一直写的是 `due_at`，这一轮是让实现追上契约。

同时新增两个同批样本的派生量：`signed_interval_error_days`（逾期为正、提前为负，
绝对值那一行看不见方向）与 `late_review_ratio`（逾期样本 / 有间隔样本）。

## 14. `advice` 成本守卫的实测表（2026-11-27，第十九轮 RC-19-4）

`advice` 的单次探测就是一整段模拟，搜索最坏要 `hi + 2` 次，所以成本按
**工作单元** `(hi+2) × days² × hi` 计量（`hi = review_limit`，0 时取 500）。
上限是 `advice_cost_limit()`（单点来源，判定 / 数值 / 百分比 / 文案全读它）。

**为什么是 3.4e8**：下界由「默认档不能自己撞自己的守卫」定——不带参数的
`advice` 就是 `days 90 / review_limit 200` = 3.27e8 单元；上界由实测定。

本机实测（native release、独立进程、`Stopwatch`，`--review-limit 200`）：

| `--days` | 工作单元 | 占上限 | 实测 |
|---|---|---|---|
| 12 | 5.8e6 | 2% | 0.32 s |
| 30 | 3.6e7 | 11% | 1.20 s |
| 60 | 1.5e8 | 43% | 5.36 s |
| **90（默认档）** | **3.27e8** | **96%** | **16.0 s（无参 `advice`：13–18 s）** |
| 95 | 3.65e8 | — | exit 2 |

旧上限 `2.5e9` 的同一台机器实测（这就是当初要改的理由）：

| 配置 | 工作单元 | 实测 |
|---|---|---|
| `--days 90 --review-limit 200` | 3.27e8 | 18.7 s |
| `--days 90 --review-limit 500` | 2.03e9 | 119.5 s |
| `--days 248 --review-limit 200` | 2.48e9 | 172.6 s |
| `--days 99 --review-limit 500` | 2.46e9 | **704 s（12 分钟）** |
| `--days 90 --review-limit 0`（hi=500） | 2.03e9 | 0.2 s（同一单元数、差 560 倍） |

**判据是双向的**（`cmd/recall/advice_cost_ceiling_wbtest.mbt`）：默认档必须放行、
上限档实测 ≤ 40 s（本机 16 s，留 2 倍机器余量）、上限必须 ≥ 默认档的工作单元、
且必须 ≥ `simulate_scan_limit()` 的 2.5e8。下一轮任何人想调这个数，两侧都会被
测试挡住——不许再靠拍脑袋。


### 14.1 这是「按单元数」而不是「按秒数」的守卫（第二十轮 RC-20-1，已知限制）

上表是**开发机**的实测。同一台机器上「每工作单元耗时」本身就有 10–16% 的抖动
（同一配置跑 5 次，CV 13.9%），跨档也不是常数：

| `--days` | 工作单元 | 每单元耗时 | 同配置 5 次抖动 |
|---|---|---|---|
| 20 | 1.62e7 | 42.4 ns | 15.8% |
| 40 | 6.46e7 | 38.9 ns | 9.9% |
| 60 | 1.45e8 | 52.9 ns | 13.0% |
| 80 | 2.59e8 | 60.5 ns | 10.0% |
| 90（默认档） | 3.27e8 | 54.7 ns | — |

高档比低档每单元贵 30–40%（探测次数 `hi+2` 的近似把「命中即停」的节省算没了，
而 days 越大单次模拟的常数项越重）。线性拟合 `t = -0.44 s + 5.71e-8 s/unit`，
R² = 0.991、最大残差 1.3 s——**能当量级，不能当精确换算**。

**所以守卫守的是单元数，不是墙钟。** 按本机标定（65 ns/unit）：

- 默认档 `days 90 / review_limit 200`（3.27e8 单元）：本机 ≈ 18 s，**慢 4 倍的
  机器 ≈ 70 s**；
- 上限档 3.4e8 单元：本机 ≈ 22 s，**慢 4 倍的机器 ≈ 90 s**；
- 仍然被拒的旧缺陷档 2.46e9 单元：本机实测 704 s，慢机器只会更慢。

也就是说：**在比开发机慢 4 倍以上的机器上，`advice` 的默认档可能超过 60 秒，
而守卫照样放行**。这是本轮明确记录的已知限制，不是待修缺陷——要做到真正
机器无关，需要「启动时跑一段固定校准工作量、按测得速度换算」的自适应预算，
而校准本身也要花时间、且在共享 CI 机器上测不准（我们实测同机抖动就有 13.9%）。
在拿到「跨机器可比」的证据之前，选择保持确定性优先：**同一条命令在任何机器上
的行止（放行/拒绝）完全一致**，只有耗时随机器变。

`cmd/recall/advice_cost_calibration_wbtest.mbt` 锁住了标定值与实测表的一致性
（每单元 30–70 ns、标定值 ≥ 每个观测值），避免下一轮把 65 ns 随手改坏。
